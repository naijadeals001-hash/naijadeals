# ADR-0003: Adapter-Mediated Integration Gateway for All External Providers

## Status

Accepted

## Context

NaijaDeals integrates with many external providers: payment processors, identity/KYC services, SMS and email gateways, AI model providers, cloud infrastructure, search engines, analytics platforms, government APIs, and media services. Direct coupling between business logic and provider SDKs creates vendor lock-in, testing friction, security risk, and duplicated integration code across modules.

## Decision

Route **all** external provider access through the **Integration Gateway** and a layer of **provider-specific adapters**. Business logic never calls a provider SDK or remote API directly.

## Alternatives Considered

| Alternative | Reason Not Chosen |
| --- | --- |
| Direct SDK calls from modules | Violates PROJECT_RULES.md Integration Gateway Law; creates vendor lock-in, duplicated code, and ungoverned secrets |
| Abstracted HTTP clients in each module | Better than direct SDKs, but still duplicates provider logic and does not centralize retries, failover, or observability |
| One shared HTTP client library | Insufficient; provider-specific mapping, credential handling, and failover need adapter-level abstraction |

## Consequences

### Positive

- Provider swaps happen by changing or adding an adapter, not by rewriting business logic.
- Centralized credential management, retries, failover, and observability.
- Consistent contract between domains and external providers.
- Easier testing with mock adapters in development and CI.
- Clear ownership of integration health and diagnostics.

### Negative

- Initial adapter development requires upfront effort for each provider category.
- Teams must learn the gateway contract and avoid bypassing it.
- Latency is added by routing through the gateway, though this is offset by caching, connection pooling, and batching.
- The gateway itself becomes a critical infrastructure component that must be highly available.

## Implementation Notes

- The Integration Gateway lives in `packages/integrations` or as its own deployable service boundary.
- Adapters map provider-specific request/response shapes to canonical gateway contracts.
- Adapters are replaceable, observable, and testable. See `INTEGRATION_GATEWAY.md` for the full adapter matrix.
- All secrets and provider credentials are loaded through the gateway configuration, never embedded in business code.
- Audit and telemetry must record provider calls, failures, retries, and fallback events.
