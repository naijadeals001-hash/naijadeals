# ADR-0002: Modular Monolith with Selective Microservice Split

## Status

Accepted

## Context

NaijaDeals is an enterprise super-ecosystem with many product-line domains (marketplace, logistics, finance, media, services) and a shared services backbone. The team must choose an implementation architecture that balances early delivery velocity with long-term scalability, operational clarity, and domain boundary discipline.

## Decision

Start NaijaDeals as a **modular monolith** with hard domain boundaries, then **selectively split services into microservices** when a domain justifies independent deployment, scaling, or team ownership.

## Alternatives Considered

| Alternative | Reason Not Chosen |
| --- | --- |
| Pure microservices from day one | Premature complexity, operational overhead, network fragility, and slower iteration before product-market fit is proven |
| Fully coupled monolith | Violates ARCHITECTURE.md domain boundary requirements and makes future extraction expensive |
| Serverless functions only | Cold-start latency, vendor lock-in, and stateful workflow complexity make it unsuitable for wallet, escrow, and event-driven domains |

## Consequences

### Positive

- Faster initial delivery and shared operational surface.
- Enforces domain boundaries through code structure, package separation, and event contracts from the start.
- Easier to refactor internal boundaries before committing to network boundaries.
- Shared services can be extracted first when load or operational isolation demands it.
- Reduces duplicated infrastructure, deployment complexity, and observability sprawl early.

### Negative

- Requires discipline to prevent the monolith from becoming a tightly coupled "big ball of mud."
- Shared database risk if teams bypass domain boundaries.
- Delayed independent scaling of high-load domains until split occurs.
- Event-driven contracts must be designed as if cross-service from the beginning.

## Implementation Notes

- Domain modules live under `apps/` and `packages/` with clear ownership.
- Shared services (Identity, Wallet, RBAC, Notifications, etc.) are isolated as if they will be extracted first.
- Inter-domain communication must use governed events, not direct imports or shared mutable state.
- The Integration Gateway is already treated as a separate service boundary because it abstracts all external providers.
- Future extraction candidates: Identity Service, Wallet Ledger Service, Notification Service, Audit Service, Aura AI Platform, and Integration Gateway.
- Extraction requires a separate ADR and migration plan before implementation.
